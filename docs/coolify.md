# Coolify Deployment

Coolify runs the prebuilt, verified image. It does not build the gateway from
source. GitHub Actions owns the build, scan, signature, and digest selection;
Coolify owns TLS, domains, container lifecycle, and persistent storage.

## Deployment model

```text
GitHub Actions -> GHCR (immutable digest) -> production branch -> Coolify -> Traefik -> container
```

Create one **Docker Compose** resource in Coolify, connected to this repository
and the `production` branch. The branch is generated by the first successful
release; if it does not exist yet, run the **Release** workflow once on `main`
before creating the Coolify resource. The branch contains only:

- `compose.yaml` — digest-pinned service definition.
- `release.json` — release metadata for audit.
- `README.md` — generated branch notice.

## Prerequisites

- Coolify v4 with a connected server and a working Traefik proxy.
- A DNS record for the gateway hostname.
- A GitHub source for the repository: public URL, deploy key, or GitHub App.
- Registry access to `ghcr.io` if the image package is private.
- A generated `BIFROST_ENCRYPTION_KEY` and `BIFROST_SETUP_TOKEN`.

## Registry access

GHCR packages are private by default for private repositories. Authenticate the
Coolify deployment server before the first deployment:

```bash
echo "$GHCR_READ_TOKEN" | docker login ghcr.io --username "$GHUB_USERNAME" --password-stdin
```

Use a fine-grained personal access token with `read:packages`, or make the
package public after the first release. Authenticate every server that runs the
container, including additional Coolify destinations.

## Create the Coolify resource

1. Select the target project and environment.
2. Choose **+ New** and connect the repository.
3. Select **Docker Compose** as the build strategy.
4. Set **Branch** to `production`.
5. Set **Base Directory** to `/`.
6. Set **Docker Compose Location** to `/compose.yaml`.
7. Save and deploy.

Do not point Coolify at `main`. The production branch is the deployment
contract and always references an image that passed the release gate.

## Environment

Set these values in **Configuration > Environment Variables**. Mark the secrets
as secret in Coolify.

| Variable | Required | Purpose |
|---|---|---|
| `BIFROST_ENCRYPTION_KEY` | Yes | Stable key for encrypted provider credentials. Generate once with `openssl rand -hex 32`. |
| `BIFROST_SETUP_TOKEN` | First boot | Allows creation of the first admin account. Generate with `openssl rand -hex 32`. |
| `LOG_LEVEL` | No | `debug`, `info`, `warn`, or `error`. Default `info`. |
| `LOG_STYLE` | No | `json` for production. Default `json`. |
| `GOGC` | No | Go GC target. `200` is a good default for throughput. |
| `GOMEMLIMIT` | No | Soft Go memory limit. Set to about 90% of the container memory limit. |
| `TZ` | No | Container timezone. Default `UTC`. |
| `BIFROST_CPU_LIMIT` | No | Compose CPU limit. Default `2`. |
| `BIFROST_MEMORY_LIMIT` | No | Compose memory limit. Default `2G`. |
| `BIFROST_VOLUME_NAME` | No | Persistent volume name. Default `bifrost-data`. |

`BIFROST_ENCRYPTION_KEY` must remain stable across restarts, upgrades, backups,
and restores. Losing it makes existing encrypted provider credentials
unreadable.

## Domain and TLS

Add a domain to the `bifrost` service:

- Protocol: `https`
- Container port: `8080`
- Enable HTTP to HTTPS redirect
- Enable the Coolify-managed certificate

Bifrost listens on `0.0.0.0:8080` inside the container and exposes no host port.
Coolify's proxy reaches it over the Compose network. Do not add manual Traefik
labels; Coolify owns routing.

The proxy must forward streaming responses without buffering, preserve
`X-Forwarded-For` and `X-Forwarded-Proto`, and support WebSocket upgrades for the
Realtime APIs.

## Persistent storage

The Compose definition declares a named volume:

```yaml
volumes:
  bifrost-data:
    name: "${BIFROST_VOLUME_NAME:-bifrost-data}"
```

The volume is mounted at `/app/data` and stores:

- `config.db` — configuration store when SQLite is used.
- `logs.db` — request logs when SQLite is used.
- `config.json` — optional declarative seed or file-only configuration.

The image runs as UID/GID `10001`. A new named volume inherits that ownership
from the image. A directory, bind mount, or reused volume must be writable by
`10001:10001`; do not rely on the entrypoint to repair host permissions from a
non-root process.

## Health and rollout

The image carries a health check:

```text
GET /health on 127.0.0.1:${APP_PORT}
```

Coolify detects the image health check and uses it during replacement. The
Compose manifest also sets a 45-second stop grace period, matching Bifrost's
30-second internal shutdown window.

With SQLite, run exactly one replica. A second process must not attach to the
same SQLite database.

## Backups

Coolify can schedule volume backups. For a consistent SQLite copy, stop the
container or use SQLite's online backup API from a sidecar:

```bash
docker run --rm \
  -v bifrost-data:/data:ro \
  -v "$PWD:/backup" \
  alpine:3.23 \
  sh -c 'apk add --no-cache sqlite >/dev/null && \
    sqlite3 /data/config.db ".backup /backup/config.db" && \
    sqlite3 /data/logs.db ".backup /backup/logs.db"'
```

Store the encryption key separately from the database backup. A backup without
the key cannot decrypt provider credentials.

## Automatic deployment

The release workflow updates the `production` branch and then calls the Coolify
deploy webhook. Configure two repository secrets:

| Secret | Value |
|---|---|
| `COOLIFY_WEBHOOK` | The resource deploy webhook URL from **Webhooks**. |
| `COOLIFY_TOKEN` | A Coolify API token with `deploy` permission. |

If the secrets are absent, the production branch is still updated and the
workflow reports that Coolify was not triggered. A Coolify GitHub App
integration can also deploy on push to `production`. Use one trigger, not both,
to avoid queuing two deployments for the same commit.

## Upgrade

Upgrades are automatic after a verified upstream release:

1. The sync workflow opens a pull request.
2. CI builds, smoke-tests, and scans the image.
3. The pull request merges after required checks pass.
4. The release workflow publishes the image and updates `production`.
5. Coolify pulls the new digest and replaces the container.

No manual image tag editing is required.

## Rollback

Rollback is a digest change, not a source rebuild.

1. Open the previous GitHub release and copy its `ghcr.io/...@sha256:...`
   digest from the release notes, or use Coolify's rollback list.
2. Update the Coolify service image to that digest, or redeploy the saved image.
3. Confirm `/health` and a non-streaming inference request.

The `production` branch is intentionally history-free; it is force-pushed on
every release. GitHub Releases, immutable distribution tags, and Coolify's
rollback list are the rollback sources.

## Verification

```bash
curl --fail --show-error "https://<BIFROST_HOST>/health"
curl --fail --show-error "https://<BIFROST_HOST>/api/version"

curl --fail --show-error --no-buffer \
  "https://<BIFROST_HOST>/v1/chat/completions" \
  -H 'Content-Type: application/json' \
  -H 'Authorization: Bearer <BIFROST_CREDENTIAL>' \
  --data '{"model":"<PROVIDER>/<MODEL>","stream":true,"messages":[{"role":"user","content":"Reply in three chunks"}]}'
```

Confirm that the streamed response arrives incrementally, then restart the
container and confirm that configuration survives.

## First administrator

Bifrost starts without a dashboard password. On first boot:

1. Open the domain.
2. Go to **Workspace > Config > Security**.
3. Enable password protection.
4. Create the admin account using `BIFROST_SETUP_TOKEN`.

The setup token is only checked when the first admin account is created. It is
not stored and is not needed afterward.
